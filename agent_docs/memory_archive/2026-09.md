## Gotchas & Pitfalls

- **Never touch Qt from a worker thread.** Background threads (hotkey listener, `process`/`live-preview`/`update`/`download-progress` workers) must call `App.post(...)` / `App.notify(...)` / `App.progress(...)`; the main-thread `QTimer` drains the queue. Direct tray/overlay/widget access off the main thread crashes Qt. (2026-07-19) — _Still in force, and still stated where it is read every turn: `CLAUDE.md → Key Patterns`, `agent_docs/architecture_principles.md`, `agent_docs/key-patterns.md → Threading model`. Archived only because those three carry it verbatim._
- **Keep heavy imports lazy.** Qt, `sounddevice`, `pynput`, `faster_whisper`, `numpy` are imported inside functions so `--version`/`--selftest` stay fast and headless. Hoisting them to module scope breaks the CI smoke test and CLI speed. (2026-07-19) — _Same: `CLAUDE.md → Key Patterns`, `agent_docs/key-patterns.md → Lazy heavy imports`, and `agent_docs/refactoring_guidelines.md` lists it as a refactor invariant._
- **Nothing that downloads a model hands out a progress callback.** `WhisperModel` and `onnx_asr.load_model` fetch the files themselves, and `faster_whisper.utils.download_model` hard-codes `tqdm_class=disabled_tqdm`, so the documented `snapshot_download(tqdm_class=…)` hook is only reachable for the OpenVINO backend, which calls it directly. `progress.DownloadWatcher` therefore measures the one thing all three share — the bytes landing in a directory — against the repo size from the hub metadata (`HfApi().model_info(files_metadata=True)`). Two traps it exists for: the pre-existing content of the folder is the baseline (a partial cache would otherwise start the bar at 40%), and a repo shipping several variants of the same model needs a `keep` filter or the percentage stalls — Parakeet's repo holds int8 (~0.7 GB) next to fp32 (~2.5 GB). Don't "simplify" it into a `tqdm` monkeypatch of `faster_whisper.utils`. (#110, 2026-08-17) — _The design is described in `agent_docs/key-patterns.md → progress.py`._
- **CTranslate2's `"default"` compute type is not "auto".** `"default"` keeps the precision the model was _converted_ with — float16 for every Systran/distil preset — and a CPU cannot run float16, so CTranslate2 silently widens it to float32, the slowest CPU path there is. The app mapped its own `compute_type = "auto"` to exactly that until 2026-09, so every default installation without an NVIDIA GPU transcribed in float32. CTranslate2's real `"auto"` is not the answer either: it picks the _fastest_ supported type, which on a GPU is `int8_float16`, a precision loss the GPU has no need for. `transcriber.resolve_runtime()` now resolves "auto" itself — int8 on the CPU, float16 on a CUDA GPU — against `ctranslate2.get_supported_compute_types(device)`, and falls back to CTranslate2's own resolution whenever the probe fails. Locked in by the `compute type resolution` selftest; don't "simplify" it back to a passthrough. (#168, 2026-09-06) — _Guarded by the "compute type resolution" selftest._
- **sounddevice declares `PaWasapi_IsLoopback`; the PortAudio it ships does not export it.** The trap is the contradiction, not the absence: sounddevice's own CFFI declarations _do_ declare `PaWasapi_IsLoopback`, so the API reads as one `_lib` call away — but the binary in its Windows wheel (>=0.5.6) is `PortAudio V19.7.0-devel`, which exports 13 `PaWasapi_*` symbols and not that one, and holds no `[Loopback]` device-name string in either ASCII or UTF-16 (same for the `-asio` and `arm64` builds). `WasapiSettings(exclusive, auto_convert, explicit_sample_format)` is the whole WASAPI surface offered; "loopback" appears nowhere in `sounddevice.py`. So no WASAPI loopback stream can be opened from this stack — don't "fix" the capture path by reaching for a flag that is not in the binary; it goes through a loopback/monitor **input** device instead (ADR-0009). Re-measure before assuming it still holds — artifact `sounddevice-0.5.6-py3-none-win_amd64.whl` from `pip download sounddevice --no-deps --only-binary :all: --platform win_amd64 --python-version 3.12` (DLL path inside the wheel and the dump commands: ADR-0009), and `requirements.txt` has no ceiling on `>=0.5.6`, so pip resolves past the measured version: the declaration means upstream has it, so a newer wheel makes it real, and it would then also enumerate every output a second time as `<name> [Loopback]`, which `system_audio.LOOPBACK_HINTS` already scores highest. Alternatives tracked in #192. (#191, 2026-09-10) — _Superseded in part by ADR-0010 (#194): the released Windows exe no longer runs on this binary. Still true for every source install and every non-Windows build, and still the reason not to reach for a WASAPI loopback flag that the loaded binary does not export._
- **The backend and the model preset are one choice, not two.** The OpenVINO organisation publishes IR conversions for `whisper-{tiny,base,small,medium,large-v3,large-v3-turbo}{,.en}` and `distil-whisper-large-v3` — and for nothing else in `MODEL_CHOICES`. Four presets (the German turbo CT2 fine-tune, `distil-large-v3.5`, `distil-small.en`, `distil-medium.en`) therefore cannot run on that backend, and the pairing used to be accepted by every screen and refused only by the first transcription, i.e. after the user had already spoken. `choices.OPENVINO_UNSUPPORTED_MODELS` is the single source of truth: it maps each to a working replacement, `models_for_backend()` filters both dropdowns, and `transcriber_openvino` raises from the same map. When adding a model preset, decide its OpenVINO status there — a new preset defaults to "supported" and would 404 on download. (#112, 2026-08-17) — _Locked in by the `model/backend pairing` assertions in `selftest.py` (`models_for_backend`, `openvino_supports_model`), and the rule is in `agent_docs/key-patterns.md → Backend abstraction`._
- **`--windowed` builds have `sys.stdout`/`sys.stderr` = None.** Any library that writes to them crashes — huggingface_hub's tqdm progress bar killed the OpenVINO model download with `'NoneType' object has no attribute 'write'`. `app._ensure_std_streams()` stubs them with devnull right after logging setup; keep that call early in `main()`. (2026-07-20) — _The same rule is in `agent_docs/development_notes.md` ("keep that call early in `main()`"), which is read before any packaging work._
