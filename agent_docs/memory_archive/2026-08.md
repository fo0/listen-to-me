## Gotchas & Pitfalls

- **CUDA errors surface at inference, not just at load.** The cuBLAS/cuDNN failure can appear during `model.transcribe`, so both the load path and the decode path handle the CPU fallback. Transient OOM is deliberately excluded from "GPU unavailable" so one bad run doesn't downgrade the whole session. (2026-07-19) — _Guarded by the "CUDA error detection" + "transcriber CPU fallback" selftests; the design is described in `agent_docs/key-patterns.md → Transcription + CUDA→CPU fallback`._
- **Qt-free modules must stay Qt-free.** `icons.py`, `keymap.py`, `help_content.py` import no `QtWidgets`/`QtGui` so they're testable headless and usable by `make_icon.py`/self-test. (2026-07-19) — _The current, longer module list lives in `agent_docs/key-patterns.md`._
- **requirements.txt ↔ pyproject.toml ↔ PyInstaller.** Runtime deps are listed in both files; a new dep with C extensions/data may also need a `--collect-all` in `.github/workflows/release.yml`, verified by the built exe's `--selftest`. (2026-07-19) — _Also stated in `CLAUDE.md → Dependency Management`._
- **Qt routes wheel events to hovered combos/spin boxes even while a page scrolls**, silently changing values. Every value widget on a scrollable page needs `qtutil.guard_wheel(...)` (ignore wheel until focused + StrongFocus). `SettingsWindow.__init__` sweeps with `findChildren`, but widgets created _later_ (e.g. `MuteTargetRow`) must guard themselves. (2026-07-23) — _Guarded by the wheel-guard assertions in `gui_smoke`._
- **Everything about autostart fails silently by nature.** Nobody watches a logon: a `Run` value that wasn't written, an entry Windows blocked, or a command that starts nothing all look identical to a working setup until the machine is rebooted. So `enable()` reads its own write back (`AutostartError`), `sync()` returns a user-facing problem string instead of swallowing it, `App._sync_autostart` notifies (forced), and Settings → General shows the command the OS really has on file. Keep any new autostart path verifiable the same way. (2026-07-30) — _Guarded by the "autostart reports a failed registration" selftest._
- **Only Discord's mute keybind is global out of the box.** Researched 2026-08-04 for `choices.MUTE_PRESETS`: Discord's `Ctrl+Shift+M` (Toggle Mute) fires while another window has focus; **Zoom** (`Alt+A`) and **Slack** (`Ctrl+Shift+Space`, huddle) only after the user ticks a global-shortcut option in that app; **Teams** (`Ctrl+Shift+M`) never — it has no global keybind at all (Windows 11's `Win+Alt+K` is the only system-wide route); **OBS** ships no mute hotkey but its hotkeys are global once set. This whole feature only works with _global_ keybinds, so a preset without that caveat would be a silent no-op — which is why every preset carries a `note` and ships disabled. Don't add a preset without checking this dimension first. (2026-08-04) — _The per-preset `note` in `choices.MUTE_PRESETS` carries the caveat into the UI; the "mute presets are usable" selftest asserts every preset has one._
- **A synthesized keybind competes with the keys the user is still holding.** Target apps (Discord, Teams, OBS) read their global keybind out of the one shared keyboard state, and the recording hotkey is by definition held at the moment the mute keybind goes out — it is what just started the take. With the default `<ctrl>+<alt>+<space>`, Discord's `<ctrl>+<shift>+m` arrives as Ctrl+Alt+Shift+M, and letting go of the _shared_ Ctrl a moment later releases it straight back out of a hold-mode keybind. `integrations._wait_for_quiet_modifiers` waits for `injector.modifiers_down()` to clear (≤1 s) before sending. Do **not** "fix" this the AutoHotkey way by releasing the held modifiers ourselves: a hold-mode recording hotkey reads its own modifier going up as the user letting go and stops the recording. (2026-08-04) — _Guarded by the "mute keybind waits for the hotkey" selftest._
- **A successful insertion proves nothing.** `Injector.insert()` returns after Ctrl+V (or the simulated keystrokes) went out — with no text field focused the paste lands nowhere and neither pynput nor the app can tell. So there is no "insertion failed" to react to; the only honest recovery is the clipboard, which is why `App._insert_transcript` announces every transcript that `insert()` reports as still being on the clipboard. Don't try to detect the empty-focus case (caret probing is per-app and unreliable) — keep the clipboard message. (2026-08-03) — _Guarded by the "clipboard copy is announced" selftest._
- **pynput's `Controller.type()` maps `\n`/`\t` to real Enter/Tab presses.** Every simulated-typing path must run through `injector.sanitize_typed_text` — `Injector._type` does since 2026-08-09 (before that, multi-line assistant output submitted chat messages / executed terminal lines); live typing always did. Paste is exempt: a pasted newline presses no key. Whisper output is flat by construction; the assistant response is the vector. (2026-08-09) — _Guarded by the "live typing logic" selftest (control characters never reach the stubbed keyboard)._
- **`Config.save()` never raises — it returns bool, and a failed _read_ must never cost the file.** After a load failure the in-memory data is only DEFAULTS, so the first save moves the unreadable `config.json` aside to `config.json.bad` instead of overwriting it (transient AV lock at logon = every setting gone otherwise). Callers surface `False` via notify/QMessageBox; `atomic_write_json` uses unique temp names so two processes can't corrupt each other. (2026-08-09) — _Guarded by the "config read failure never costs the file" and "config factory reset" selftests._
- **Moving the never-shown overlay bubble window segfaults Qt** (offscreen platform, reproducible: the crash lands in an unrelated `QDialog.__init__` later). `reposition_bubble()` is only meaningful while the bubble is up — `_show_bubble` positions it right before showing — so every new caller guards with `self.bubble.isVisible()`. Don't "simplify" that guard away. (2026-08-13) — _A regression takes `gui_smoke` down outright, which is the guard._

## External Dependencies

- **pynput >= 1.8 changed `HotKey.parse` semantics** — non-modifier special keys (`<f9>`, `<space>`, arrows) now parse to `KeyCode.from_vk(...)` instead of `Key` members; only Ctrl/Alt/Shift/Cmd stay `Key` instances. `Listener.canonical` converts the same way, so press-matching still works — but `isinstance(key, KeyCode)` no longer means "character key". `combo_flags` detects typability via `char`/space-vk/known-special-vks; keep any new key-classification logic compatible with both 1.7.x and 1.8.x (requirement is `>=1.7.7`, CI/exe builds pick latest). (2026-07-21) — _Guarded by the "key picker key mapping" selftest._
- **pynput uppercases a character key while its Controller holds Shift — and Windows then sends it as _text_, not as a key.** `Controller._resolve` turns `KeyCode.from_char("m")` into `"M"` whenever that same controller has Shift down; the win32 backend can't reach `"M"` without a modifier, so it injects a Unicode packet (`KEYBDINPUT.UNICODE`, `wVk=0`) instead of a key event. Global keybind hooks (Discord, Teams, OBS) never see VK_M, and the character lands as literal text in the focused field. That is exactly how the mute integration broke for Discord's default `<ctrl>+<shift>+m` while the shipped `<f9>` preset (parsed straight to a vk) always worked. `integrations._synth_keys` substitutes the vk up front — never synthesize a chord from a char-only `KeyCode`. (2026-08-04) — _Guarded by the "mute keybind uses virtual keys" selftest._
